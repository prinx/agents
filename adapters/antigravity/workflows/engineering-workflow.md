# Engineering Workflow

Follow the risk-based permission policy in the workflow-toolkit rule. Deployment still requires an explicit human request, even if a command is otherwise allowed.

Default to `prototype-first`: run a short discovery for the smallest valuable first feature, get explicit approval of its simple plan, then build and test it without routine confirmations. Guided/checkpointed and autonomous modes are available only when requested. Pause only for material scope/goal, security/cost/privacy/credential, destructive, remote, deployment, or explicit checkpoint decisions. Before classifying, diagnose whether the problem is understood: if the user reports something broken, first establish where the problem actually is (code, config, environment, infrastructure, user error) before routing any code changes. Never modify code to fix a problem that has not been diagnosed. Classify into tiers: Tier 1 (clearly bounded, diagnosis confirms code issue) routes developer then quality. Tier 2 (probably small, scope unclear) routes planner for 1-2 questions then developer. Tier 3 (clearly complex) routes full planner workflow. Default to tier 2 when unsure. On every handoff, scan available skills and tell the subagent which to load. Route UI work to `frontend-design` (or `ui-ux` fallback), test work to `unit-testing`/`feature-testing`/`e2e-testing`, review work to `quality-review`, unclear scope to `requirements-gathering`, architecture to `solution-design`, ticket breakdown to `task-breakdown`, Git checks to `branch-safely`, deployment to `deploy`/`deploy-vercel`, docs to `documentation`, and production checks to `monitoring`. The user should never need to request a skill — you route it automatically. Do not skip routing for small changes. Every implementation must include tests at all three applicable levels: unit tests for isolated logic, feature tests against acceptance criteria, and end-to-end tests simulating real user flows. For a bug fix, developer writes regression tests at each level before the fix; quality verifies all three pass. For user-facing work, first check for and load `frontend-design`; if unavailable, use the included `ui-ux` fallback. Respect approved scope, existing conventions, accessibility, responsiveness, and simplicity; do not add decorative features or a new design system unless requested. At completion give the actual local URL when known, otherwise exact commands and short steps organized by test level, then ask whether to test, fix, adjust, or start the next feature; do not proceed automatically unless autonomous mode was explicitly selected.

Use the workflow-toolkit rule and relevant skill. Classify the request, create dynamic specialist subagents as necessary, keep artifact ownership explicit, relay planner discovery questions to the human, and stop until required answers arrive. After the planner creates proposed requirements, plan, and backlog, summarize only essential decisions and wait for explicit human approval before developer handoff; never infer approval from silence. At that approval gate, record checkpointed or autonomous delivery; both modes retain planning and deployment approval gates. Check every milestone against requirements and confirmed decisions before starting it; complete and review it before the next milestone, with human review before and after milestones only in checkpointed mode. Quality owns `.agents/artifacts/local-test.md` and must determine the real local path from repository evidence, not guesses. Before final user-facing `PASS`, it requires a valid local test path or reports `BLOCKED` or `PASS_WITH_NOTES` with what is missing. At completion, summarize the exact commands and URL from that artifact directly to the human, then give the next action.
