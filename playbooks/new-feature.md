# New Feature Playbook

**Hard gates — never skip:** Developer always hands off to quality. Quality must produce `qa-report.md` and `review.md`. Never declare work done without these artifacts.

1. Orchestrator records `prototype-first` delivery unless the human explicitly requests guided/checkpointed or autonomous delivery.
2. Planner asks only the short questions needed to establish goal, users, constraints, smallest useful first result, and success criteria. Planner includes a test strategy in `plan.md`: which test levels apply (unit, feature, end-to-end), what each covers, and how the developer will verify them.
3. Planner creates proposed first-feature requirements, a simple stack, lightweight plan, small backlog, and optional short future-ideas list. The human explicitly approves this first-feature plan.
4. Orchestrator identifies which skills match the work and tells the developer to load them (for example `frontend-design`/`ui-ux` for UI work, `unit-testing`/`feature-testing`/`e2e-testing` for tests). The user should never need to request a skill explicitly.
5. Developer implements the approved first feature test-first at three levels: unit tests for isolated logic and edge cases, feature tests against each acceptance criterion, and end-to-end tests simulating the real user journey. Loads all dispatched skills. Respect approved scope, existing conventions, accessibility, responsiveness, and simplicity; do not add decorative features or a new design system unless requested. Choose the smallest working solution and avoid unnecessary infrastructure or abstractions. **Developer must hand off to quality — work is not done until quality reviews.**
   - **Risk-triggered evidence only:** Security review triggers for authentication, authorization, sessions, secrets/credentials, payments, sensitive personal data, security controls, or an untrusted-input/external-data boundary. Accessibility review triggers for a user-facing interface, navigation, form, or interactive control. Performance review triggers for a hot path, database query pattern, N+1 query risk, response-time budget, large data set processing, memory allocation, bundle size, or caching behavior. For each trigger, developer records the trigger, change-specific checks, results, and remaining risk; quality verifies it. Security covers the relevant boundary, access control, data exposure, and safe handling; accessibility covers keyboard path, semantic/accessible name, focus behavior, and visual readability; performance covers the affected path, measured or estimated cost, and whether the change stays within the existing budget. Missing triggered evidence or an unresolved issue blocks QA/review. Non-triggered changes need no evidence; do not add scanners, formal compliance, reliability, or architecture review.
6. Quality performs three sequential phases: run tests at all three levels, inspect the diff for correctness/security/scope, then classify findings as blocking or advisory. It writes `local-test.md` organized by test level, QA `PASS`, `FAIL`, `BLOCKED`, or `PASS_WITH_NOTES`, and review `APPROVE` or `REQUEST CHANGES`. It gives the simplest evidence-based test path: a local URL when known, otherwise exact commands and short steps. **Quality is mandatory — never skip.**
7. Orchestrator updates backlog, memory, and state. **Orchestrator must confirm `qa-report.md` and `review.md` exist before declaring work done.** Logs the completed feature in `state.md` with: feature name, key decisions, known issues, dependencies, and QA outcome. Gives the local test handoff organized by test level, and asks whether the human wants to test, fix, adjust, or start the next feature. Do not automatically plan or build the next major feature unless autonomous mode was explicitly selected.
8. Pause for approval only for a material scope/goal change; security, cost, privacy, credential, destructive, remote, or deployment decision; or an explicit user-requested checkpoint. Deploy only on explicit human request after both quality gates pass.
